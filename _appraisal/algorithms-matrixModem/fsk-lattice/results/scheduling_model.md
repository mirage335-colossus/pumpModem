# Scheduling rules against measured stage costs

Generated by `scheduling_model.py`. Arithmetic on the rates measured on a full RTX PRO 6000
Blackwell with a 13.6-CPU host; not a running scheduler. Theoretical calculation.

## 1. Is a shared GPU work-conserving?

Each stage's rate while sharing, divided by its rate alone (32,768 dwells per call), and the sum.
A sum of 1 means the GPU time was divided, not lost.

| Search route | Transform route | search share | transform share | sum |
|---|---|---:|---:|---:|
| direct | cuFFT | 0.859 | 0.093 | 0.952 |
| direct | FP16 matrix DFT | 0.880 | 0.079 | 0.959 |
| direct | INT8 matrix DFT | 0.842 | 0.119 | 0.960 |
| matrix | cuFFT | 0.846 | 0.168 | 1.014 |
| matrix | FP16 matrix DFT | 0.888 | 0.146 | 1.034 |
| matrix | INT8 matrix DFT | 0.812 | 0.210 | 1.022 |

## 2. Time to clear a queued workload

A workload is a number of dwell transforms (dwells times timing hypotheses) and a number of full
block decodes. The GPU is taken as work-conserving (section 1: within about 5%). The CPU has no
measured decode route, so it can only take transforms. Rules:

- `stage race`: what the prototype did. Transform on the GPU by the route that won the 0.5 s race
  under load (FP16 matrix DFT at 32768 per call), decode on the GPU, CPU idle.
- `CPU FFT, GPU search`: a fixed rule. All transforms on the CPU, all decodes on the GPU.
- `cost-based`: each stage on the GPU by its cheapest measured route and portion size (cuFFT at 4096
  per call), with the CPU taking transform portions whenever it is free.
