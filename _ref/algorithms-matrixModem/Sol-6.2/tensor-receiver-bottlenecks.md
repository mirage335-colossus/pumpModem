# Tensor Core bottlenecks and modem co-design

24 November 2026 · Matrix Modem experiment and literature review

The repeated-FSK receiver has two independent expensive stages. Projection extracts soft evidence from IQ. Codeword scoring evaluates one dense dot product for each legal row and payload. In the original long-frame comparison, cuFFT plus pedantic FP32 scoring took 7.047 ms, sliding projection plus FP32 took 4.762 ms, and sliding projection plus FP16 Tensor Core scoring took 2.072 ms. The reported 3.40× combined both changes. Holding the sliding frontend fixed, the scorer alone went from 3.811 to 1.122 ms, a 3.40× scorer gain and a 2.30× IQ-to-decision gain. [Original matched receiver run](tensor-reception-results.md)

## How much of Tensor Core performance did the scorer use?

The long scorer evaluated a dense real matrix product of shape `2048 × 32768 × 2048`. Sustained replay originally reached 258.05 nominal dense TFLOP/s, with 56–57% Tensor activity, 97% SM activity, approximately 30% GPM warp occupancy, and 39–41% GPM DRAM-bandwidth utilization. Whole sliding-frontend replay reached 28–29% Tensor activity. GPM Tensor activity measures time spent doing Tensor operations. The FP16 inputs, FP32 accumulator, hardware clocks and lack of structural sparsity all matter when interpreting throughput. NVIDIA's 4 PFLOP/s headline is for FP4. Based on the documented dense GB202 FP16-with-FP32-accumulation rate per SM and the measured 188 SMs at 2.38–2.39 GHz, the applicable arithmetic peak was approximately 459–460 TFLOP/s. This is an architecture-and-clock estimate. The 258 TFLOP/s figure counts codeword dots and includes conversion and argmax. [NVIDIA Server Edition rates](https://www.nvidia.com/en-us/data-center/rtx-pro-6000-blackwell-server-edition/), [GB202 architectural rate and precision table](https://www.nvidia.com/content/dam/en-zz/Solutions/design-visualization/quadro-product-literature/pdf/NVIDIA-RTX-Blackwell-PRO-GPU-Architecture-v1_1.pdf), [NVML metric definitions](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlGpmEnums.html)

A simple time-budget check explains most of the difference between the two utilization figures. The sustained scorer had roughly 56.5% Tensor activity. A 1.122 ms scorer in a 2.072 ms receiver gives an estimated 30.6% full-pipeline activity. With the slower 4.358 ms cuFFT pipeline that estimate is 14.5%. The observed 28–29% and 13–14%, respectively, are close despite distinct steady-replay and per-opportunity timings. The projection and transfer path consumed time without adding dense scores. With the original 0.938 ms sliding stage held fixed, a hypothetical instantaneous scorer would yield about 2.18× more end-to-end speed. The same dense FP16 arithmetic by itself has a roughly 0.60 ms best-case duration at the estimated rate, before packing, reduction or other work. Keeping the sliding stage and replacing the scorer with ideal-rate arithmetic gives roughly 1.34× further speedup. These same-work bounds leave scope for algorithmic changes on either side.

### Global memory round trip

| Long scorer data | Size | What the implementation does |
| --- | ---: | --- |
| FP16 contrast matrix | 8 MiB | Convert the 16 MiB FP32 frontend buffer before GEMM |
| FP16 codebook | 128 MiB | Persistent device operand; additional FP32 copy serves the reference route |
| FP32 scores | 256 MiB | Write all 67,108,864 scores to device-global memory, then read all for argmax |
| Logical score round trip | 512 MiB | Count one write and one read per score; physical DRAM bytes can differ |

The receiver returns one winning row and word. Its output matrix is twice the GPU's 128 MiB L2 cache, confirmed by the follow-up's CUDA device properties. The full result cannot remain there between GEMM and reduction. L2 can still serve part of the traffic. At 939 opportunities/s, the nominal score round trip alone represents roughly 504 GB/s of logical memory accesses. Adding one read each of the FP16 operands gives roughly 638 GB/s. These are consistent in magnitude with the device-level 39–41% DRAM bandwidth figure and a 1,597 GB/s advertised maximum. They do not identify the exact bytes or stalls of any kernel. Even if all 512 MiB went through GDDR7, dividing by advertised bandwidth gives 0.336 ms at peak transfer speed. This is a bandwidth equivalence. Memory and arithmetic can overlap, so removing the buffer would not necessarily save that much time. The older Nsight Compute attempt on this provider could not read privileged counters. [Original projection profiling outcome](tensor-execution-evidence.md#matrix-regular-grid-projection-probe)

An immediate tile reduction tests reuse with existing cuBLAS. A future fused kernel could combine the GEMM epilogue, the per-row additive likelihood term and a deterministic local maximum before writing a partial to global memory. It would remove the full score round trip. This is distinct from tiling, which still logically writes and reads every score. NVIDIA's Hopper CUTLASS Top-K epilogue demonstrates the general mechanism, while this receiver needs a qualified SM120 path with its own tie and accumulation rules. [CUTLASS Hopper Top-K example](https://github.com/NVIDIA/cutlass/tree/main/examples/61_hopper_gemm_with_topk_and_softmax), [cuBLASDx register and shared-memory interfaces](https://docs.nvidia.com/cuda/cublasdx/using_cublasdx.html)

The sign table also has a compact representation. Its ±1 operands are exact in FP16 and representable in FP4. Packing the signs and scaling the received contrasts for a block-scaled FP4 route could reduce operand traffic and raise arithmetic throughput. FP32 accumulation, acceptable ranking near a threshold and efficient output reduction would still need separate validation. The older NVFP4 test compared tone projections on a different geometry. [Low-precision projection experiment](tensor-execution-evidence.md#matrix-regular-grid-projection-probe)

### Same-GPU score-tiling test

The 2,048-feature search evaluated all 32,768 codewords and 2,048 rows, either as one product or sequential column tiles immediately reduced to a local maximum. The GPU returns the maximum across tile winners. Codeword order and score ties are preserved. The 512-feature shape ran the same control. Across 12 input and history settings per shape, no tiled winner, threshold decision or reported maximum score differed from the full-matrix result. The timing experiment used 204 wall samples per shape and width with rotating order. CUDA-event stage figures come from separate instrumented invocations.

| Codewords per tile, long shape | Score buffer | Nominal active FP16 operands and FP32 results | Convert and bound | GEMM | Reduction | Scorer wall |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 32,768 | 256 MiB | 392 MiB | 0.103 ms | 0.768 ms | 0.260 ms | 2.833 ms |
| 16,384 | 128 MiB | 200 MiB | 0.101 ms | 0.854 ms | 0.244 ms | 2.862 ms |
| 8,192 | 64 MiB | 104 MiB | 0.101 ms | 1.034 ms | 0.205 ms | 2.917 ms |
| 4,096 | 32 MiB | 56 MiB | 0.100 ms | 0.938 ms | 0.236 ms | 2.829 ms |

The 8,192-word tile reduced the argmax stage by about 0.055 ms. Its summed GEMM events rose by about 0.266 ms. The GEMM intervals include any queue gap between their bounding events. They are not isolated Tensor-pipeline times. Score tiling kept less memory live, with no persuasive long-shape latency improvement. It did not remove per-score stores and loads. CPU-visible timings on this pod varied considerably and the event medians come from independently timed stage runs, so adding the event columns is not a reconstruction of wall time. The 512-feature 8,192-word case had an approximately 9% shorter wall median, 0.819 versus 0.901 ms, on this one host. None of the timings qualifies a universal tile width. Fusing reduction into the multiply remains a different, untested optimization.

In separate ten-second scoring replays, the full and 8,192-word-tile routes produced 153.12 and 142.97 nominal dense TFLOP/s. Median one-second interior GPM reported, respectively, 35% and 32% Tensor activity, 59.5% and 61% SM activity, and **24% and 12% DRAM-bandwidth utilization**. The DRAM figure fell much more than throughput. This is consistent with cache reuse or less off-chip traffic per search, without identifying individual cache hits or attributing the entire drop to them. Both feed rates were well below the prior run's 258 TFLOP/s and 97% SM activity, on a pod with substantial wall-time variation. A CUDA Graph or longer submit batch would test host-feed effects before extrapolating these rates to a saturated GPU. No hardware ceiling follows from the slower pod.

## Where channel filtering changes the calculation

In the exact-lag drift fixture, the eight CPFSK tone centers ran from −62.5 to +62.5 Hz before an unknown ±25 Hz absolute offset and a few hertz of drift. Most captured noise occupied dimensions outside this family. For aligned noisy observations `x=s+n₁` and `y=s+n₂` with unit noise power per complex sample and signal energy `E`, the noise variance of the raw complex dot is `2E+N`. An ideal orthonormal reduction from `N=2048` to `N=256` at the same retained energy would improve the ratio of squared signal to correlation variance by about 7.5 dB at +20 dB-Hz. This is an ideal white-noise calculation. A physical FIR has correlated output samples and can share input noise across adjacent looks. [Original raw-history model and fixture](received-history-drift.md)

### Same-capture FIR experiment

The native CPU comparison used a 161-tap Blackman-windowed low-pass with 140 Hz cutoff and decimated by eight to 400 complex samples/s. Each 0.64 s repeat has a 25 ms guard at both ends, shared with the full-rate comparator. The guard ensures that the filtered samples retained in one repeat never reuse raw input noise from the other. For each drift candidate, the raw correlation is normalized by the conditional covariance of the filtered noise, including its intersample correlations. The filtered known-template route uses generalized least squares. The full-rate known-template route uses the factored FFT. Every path covers the same three drift hypotheses, same timing, and for known templates the same additional 33 absolute offsets.

| Drift fixture | Correct, raw full band | Correct, raw filtered |
| --- | ---: | ---: |
| +10 dB-Hz | 0/48 | 0/48 |
| +20 dB-Hz | 2/48 | 48/48 |
| +28 dB-Hz, grid | 48/48 | 48/48 |
| +28 dB-Hz, fractional | 48/48 | 48/48 |
| +28 dB-Hz, halfway phase step | 0/48 | 0/48 |

The last row still produced 48 accepted wrong drift labels on each path. In 1,024 separately seeded white-noise trials, each raw path and each known-template path accepted one trial at the nominal 0.001 threshold. Sixteen clean checks passed, with at least 99.88% retained in-band signal power at corresponding guarded centers. Over the checked 1 Hz grid the minimum gain through 95 Hz was −0.032 dB and the maximum gain above 200 Hz was −75.44 dB. Adding 350 Hz of absolute offset left at most 0.0073% of the clean signal energy through this narrow filter. This illustrates why the full-band correlator's frequency-offset invariance can be useful as an acquisition fallback. The filter assumes a coarse frequency estimate or public bound.

In a local repeat of the +20 dB-Hz group, raw scoring averaged 7.40 µs at full rate and 5.87 µs on the reduced signal. The filter added 54.1 µs, making the complete small CPU raw path about 8× slower. The known-template route fell from 144 µs to about 106 µs including the filter, a 1.36× gain for these particular implementations. One-time template and covariance preparation is outside those timings. This is a sensitivity result for the raw detector and a modest timing improvement for a much larger reference bank. It does not measure receiver acceleration when the narrow IQ is delivered directly by radio hardware or when a shared filter serves multiple searches. [Native FIR replication commands](../../../_appraisal/algorithms-matrixModem/tensor-reception/README.md)

### Broad FSK bank and exact FFT work reduction

The large codeword experiment already discards out-of-tone dimensions during the projection. The union of all tone centers, candidate offsets and signed tone labels runs from −1,018.75 to +1,000 Hz before allowing for spectral sidelobes or channel spread. A fixed 1,600 complex samples/s initial channel would miss public hypotheses. After center isolation, the per-hop union is −318.75 to +300 Hz. A tracking branch at 800 complex samples/s leaves some transition room, with 64 samples per 80 ms look and one sample per 1.25 ms candidate timing increment. Prior uncertainty and channel tails determine whether that branch is adequate. Nine permanently active 800-sample/s channels would produce 7,200 filtered complex samples/s, more than the 3,200 input samples/s. Dehopping a known schedule or using a shared polyphase channelizer can avoid paying for every independent filter. A full-band acquisition or reacquisition path must remain available where the narrow branch has insufficient coverage. [Harris, Dick and Rice on efficient polyphase channelization](https://doi.org/10.1109/TMTT.2003.809176)

The fixture's selected indices on the original 1,024-point FFT are all even. The exact projection of the same 256 IQ samples at original bin `k` is the 512-point transform's bin `k/2`. The reduced transform kept every candidate and used the original phase correction. In the same-device run all three frontends passed the direct DFT check, the quiet/resumption sequence, and all 220 matched decisions, words and timing/frequency winners. The largest score change from the original FFT was 0.000351 for the short transform and 0.001129 for the sliding transform. The short transform cut explicit long-case frontend allocation from 57.1 to 41.1 MiB.

| Projection method | 512-feature frontend | 2,048-feature frontend | 2,048-feature complete with Tensor scoring |
| --- | ---: | ---: | ---: |
| 1,024-point cuFFT | 1.147 ms | 3.827 ms | 6.432 ms |
| 512-point cuFFT | 1.021 ms | 4.139 ms | 7.915 ms |
| Sliding projections | 0.839 ms | 1.615 ms | 5.032 ms |

These are Tensor-route host-wall medians across the same fixed suite, with the executables run in separate blocks. Frontend time spans host transfer and synchronized tone features. This host showed long-tailed wall times even in the unrelated readback stage. Halving zero padding is an exact computation and storage reduction for this grid. The timing sample demonstrates no reliable long-frame speedup for short cuFFT. Sliding projection remains the faster long frontend in this run as well as in the prior run.

Downconversion and decimation can remove IQ work and improve the raw correlation statistic. Once the same contrast vector is available for each of the same public timing, frequency and codeword hypotheses, they leave the dense codeword workload unchanged. Further speedup would come from shrinking the uncertainty range with qualified evidence, choosing a code that factors, or changing materialization and reductions. Several routes can share a front-end improvement, including cuFFT.

I found directly demonstrated Tensor Core pilot processing and demodulation components, and full GPU radio receivers that were designed around computational structure. The reviewed work leaves open a complete weak-signal, single-channel FSK format selected for both high Tensor Core utilization and HF sensitivity. A useful closest analogy is an acquisition pattern that can be isolated or dechirped cheaply, followed by a dense matrix only when many physically meaningful alternatives share operands. Timing, bandwidth and noise models from wideband MIMO and OTFS do not transfer directly.

The current codebook deliberately uses nonlinear signs per payload and feature. A different binary linear format could expose an exact fast transform. If feature `k` is transmitted as sign `(-1)^(w·gₖ ⊕ cₖ)` with a known binary generator column `gₖ` and scrambling bit `cₖ`, accumulate weighted feature contrasts by `gₖ`. A length-32,768 Walsh–Hadamard transform evaluates the additive metric for all 15-bit words in a row. At 2,048 features that is roughly 494,000 add/subtract operations per row, against 134 million dense FLOPs under two-FLOP FMA counting. This is an exact operation count for the proposed code structure, with no measured speed or sensitivity claim. Generator rank, distance, constrained-code acceptance, other link assumptions and joint channel memory need testing before replacing the random codebook. [Classical fast transform decoding](https://doi.org/10.1109/TIT.1986.1057189)
