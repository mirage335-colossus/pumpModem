# Reproducing the isolated FP4 study

This guide reproduces the isolated three-carrier study in [`protocol.md`](protocol.md). It does not change the ordinary Robust receiver or qualify a precision policy for operational admission. Run the commands from the repository root unless a section says otherwise. The packaged `SHA256SUMS` and per-run JSON records are authoritative for source, executable, input and environment identity; verify them before comparing results.

## Source and evidence layout

The deterministic archive is `technical-evidence.tar.gz`. Its device records are under `gpu-5090/results/`, `gpu-pro/results/` and `gpu-mig/results/`; `holdout-evidence/` contains the frozen-case evidence and executed tools. It includes development and holdout manifests, hashes and per-case run records, but not the full raw IQ payloads. It also contains two raw comparison captures and the frozen exporter/source snapshots needed to regenerate the complete inputs. The archive's `SHA256SUMS` covers every packaged file. Extract it outside the source tree and set paths explicitly:

```bash
export SRC="$PWD"
export STUDY="$SRC/docs/validation-data/triad-v3/2026-11-01-fp4"
export OUT="/path/to/new-fp4-run"
mkdir -p "$OUT/extracted"
sha256sum -c "$STUDY/SHA256SUMS"
tar -xzf "$STUDY/technical-evidence.tar.gz" -C "$OUT/extracted"
export EVIDENCE="$OUT/extracted/technical-evidence"
export DEV_RECORDS="$EVIDENCE/development-inputs/inputs"
export HOLDOUT_RECORDS="$EVIDENCE/holdout-evidence/holdout-inputs"
(cd "$EVIDENCE/.." && sha256sum -c technical-evidence/SHA256SUMS)
```

`DEV_RECORDS` and `HOLDOUT_RECORDS` hold metadata, not complete receiver-ready captures. The two packed development IQ examples are `boundary-cn-10-r0` and `large-bank`; use them for bounded replay or regenerate the exact dataset into a new scratch output directory from the frozen exporter and source snapshots. Do not overwrite an existing run directory. Each campaign, probe and profile writes a fresh output directory.

The packager defaults to a no-write plan. After the study owner confirms the result graph is complete, build the archive with:

```bash
python3 "$STUDY/package-evidence.py" \
  --evidence-root "$SRC/local-evidence/triad-fp4-20261101" \
  --source-root "$SRC" --output "$OUT/technical-evidence.tar.gz"
```

Add `--build` to write the archive. The builder excludes raw Nsight `.nsys-rep` files and accepts SQLite traces only when their hashes match `profile-redaction.json`; it fails on unapproved selected SQLite files. A dry-run prints the complete ordered member list and byte count without creating the archive.

The source tree contains the repaired holdout generator. The archived `holdout-evidence/generate-holdout.py` is the exact generator copy executed before metadata repair; its earlier summary overstated the strict-all policy and used an incorrect HF hypothesis count. Its case definitions, seeds and frozen source hashes match the repaired helper. The repaired helper corrects those descriptions only. Since raw holdout IQ is not packaged, exact regeneration from the frozen cases and seeds is part of reproducing the dataset; it does not create a new statistical holdout. A new independent validation requires fresh roots after policy selection.

## Sampled inputs and seed provenance

Development captures are generated by `generate-inputs.py` using the sampled waveform exporter. The original development exporter source and executable are preserved under `$EVIDENCE/source-before-seed-extension/`; the source SHA-256 is `99a268643103cac3e5fb351f1179dc8a0fa3a22dc00c909461b57db1e2315ccc` and the binary SHA-256 is `4546860cfe81d5e0076ab0f1381221d9a5c6123e7f27989f4441b177f26b1227`. The helper verifies its source fingerprint, so reproduce into a scratch source tree by placing the archived source snapshot and exact executable at the paths expected by the helper, then run `generate-inputs.py --output-root "$OUT/development-inputs"`. Its development seed recipe is `base = 50000 + 100 * case_index`, with `--seed=base+3`, `--key-seed=base+1`, and `--channel-seed=base+2`. Its OpenSSL mask is `~0x200000000000000:~0x20000000000:~0x0:~0x0:~0x0`; compare output hashes within each pair. This times whole sampled exports, not isolated AES instructions.

## Paired sampled-waveform campaigns

`run-campaign.py` consumes the exact archived sampled captures, uses the complete declared CFO/lag/epoch bank, and writes one result per capture and policy. It requires a fresh output directory. Stages are `screen`, `diagnostic`, `performance` and `holdout`. The screen compares FP64, strict FP32, NVFP4 and MXFP4; diagnostic separates strict/template-only/observation-only/both quantization against FP64; performance repeats the boundary capture for timing and does not create new physical trials; holdout compares paired FP64 and NVFP4 and does not claim calibrated noise admission.

Example development screen for a boundary case:

```bash
"$PY" "$STUDY/run-campaign.py" --root "$SRC" \
  --inputs "$OUT/development-inputs" --output "$OUT/screen-cn10" --stage screen \
  --phase-states 512 --pattern 'boundary-cn-10-r0' --max-seconds 800
```

After exact holdout regeneration and hash checks, this replays one frozen-seed capture:

```bash
"$PY" "$STUDY/run-campaign.py" --root "$SRC" \
  --inputs "$OUT/holdout-inputs" --output "$OUT/holdout-target" \
  --stage holdout --phase-states 512 --pattern 'h1-target-cn-08-r000' \
  --max-seconds 800
```

The driver records the resolved argv and results in its index. Its native-FP4 decision is an experimental paired comparison and remains uncalibrated. To reproduce the profile helper's additional explicit exhaustive strict-all pass, run `profile-receiver.py` below; strict-all is not implied by the holdout stage. A selected campaign helper must not be interpreted as authorizing candidate pruning.

### Fixed-bank whole-scan workspace

The final whole-scan experiment covers a fixed **B=1, flat, Q=3** workload: one `boundary-cn-10-r0` sampled observation (requested 256 seconds, actual transmitted duration 337.2 seconds, truth bit 0), one flat/none channel tap, 4 public bit×epoch candidates, three CFO values (`−0.01, 0, +0.01 Hz`) and three lags (0–2), or 36 correlation hypotheses. It uses the same FP32 graph inference and FP64 reductions for each correlation arithmetic mode. `A,B,A` checks use a zero-input B as a stale-state falsifier; these replays are not independent reception trials. The resulting one-capture admissions do not calibrate the operational noise tail.

Reproduce the three recorded precision runs in a CUDA PyTorch environment, with a fresh output path for each:

```bash
for precision in fp64 fp32 native-fp4; do
  "$PY" "$SRC/tools/triad-scan-workspace.py" \
    "$DEV_RECORDS/boundary-cn-10-r0" \
    --output "$OUT/whole-scan-${precision}.json" --device cuda:0 \
    --precision "$precision" --representation-mode both \
    --fused-reconstruction --inference-precision fp32 \
    --inference-implementation graph-fp64 --native-format nvfp4 \
    --trim-zero-suffix --cfo-hz -0.01 0.0 0.01 \
    --lag-start 0 --lag-stop 2 --lag-step 1 \
    --sample-rate 64 --block-samples 256 \
    --candidate-tile 16 --frequency-tile 4 --column-tile 128 \
    --gram-cache-mib 16 --receiver-memory-mib 8192 \
    --template-cache-mib 256 --max-block-output-mib 1024 \
    --phase-states 512 --relative-phase-states 8 \
    --residual-frequency-bound 0.02 --residual-frequency-std 0.003 \
    --frequency-correlation 1000 --phase-diffusion 0.00872665 \
    --attempt-spacing 60 --duration-alternatives 1 --model-alternatives 1 \
    --repeats 7 --repeat-observations 1 --workspace-memory-mib 32768
done
```

For the selected RTX 5090 and full RTX PRO 6000 results, all three modes reproduced A after B bit-for-bit and stayed within `2e-5` absolute score error versus the corresponding non-workspace baseline. Median warmed complete replay timings ranged from 13.2 to 15.0 ms on RTX 5090 and 15.1 to 17.3 ms on PRO 6000; workspace preparation was 0.33–0.41 s and 0.15–0.18 s, respectively. These figures describe this fixed bank and single capture only. NVFP4's bit decision agreed on this point; it remains an uncalibrated experimental policy.

```bash
for name in development-hf-v2 development-v1 diagnostic-v1 holdout-v1 performance-v1 \
  large-fp32-v1.json large-native-fp4-v1.json large-parent-v1.json nsys-large-parent.json \

done
MPLCONFIGDIR="$OUT/matplotlib-cache" python3 "$STUDY/analyse-results.py" \
  --results-root "$OUT/analysis-inputs" --out-dir "$OUT/sensitivity-analysis" \
  --rate-usd-hour 1.197
```

The reproduction analysis should retain 753 paired holdout cases, 1,506 completed policy evaluations, 40 holdout marginal groups and 20 paired group comparisons. Path strings differ from the original workspace; numerical counts and confidence intervals should agree. Analysis of the frozen seed set remains reproduction, not new validation.

Use paired observations for numerical comparisons and independent physical seeds for final evaluation. Keep template quantization and observation quantization results separate. Retain failures and numerical mismatches. Throughput from a kernel, repeated timing copy or correlation-only comparison is not complete receiver throughput. The existing holdout is not large enough to establish a probability as small as (10^{-4}) per day; do not infer operational false-admission calibration from zero observed admissions. Reception, admission, sensitivity and cost claims belong to the accompanying analysis and must state their confidence bounds and unresolved assumptions.
