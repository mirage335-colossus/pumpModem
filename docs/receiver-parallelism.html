Source-derived dependencies

Does DSP require the empty spaces?

Some ordered results are mathematically necessary. The current separation between preparation and a worker wave is an implementation choice. More buffering helps only when the next useful work is knowable and the buffer can be owned safely.

Already captured samples do not drift while waiting

The receiver advances phase/clock hypotheses and Gaussian time steps using captured sample coordinates and block centres. CPU delay adds processing latency and may increase future capture-buffer pressure; it does not add phase uncertainty to an unchanged sample array. A larger coherent integration interval changes the model. A larger computational batch that preserves the original blocks need not.

The adaptive next state is genuinely causal

Current emissions feed the timing observation and global state cap before the next adaptive state set is known. A second buffer does not remove that dependency. Fixed-affine template geometry is more predictable from its initial anchor and next sample coordinates, although Gaussian seeding and updates still retain their chronological order.

Buffering is already present, but not a pipeline

The headless stream path buffers a complete public window before bit reception. Its default input-chunk limit is 16,384 samples—2.731 seconds at 6 kHz—and is configurable; that limit is not a compulsory sleep or a physical processing deadline. This path has no hardware feedback/tuning deadline or live GUI connection to force the illustrated joins.

triad_stream_receiver.py:70 · triad_stream_receiver.py:191 · triad_stream_receiver.py:326

A producer needs an independent ownership boundary

The native tile producer owns one pipe and mutable LRU state. Current jobs pin their inputs, which is useful for a future two-buffer design, but dispatch_group currently combines submission, joining and cleanup. Overlap needs separate preparation/dispatch/join phases, protected leases, one aggregate CPU budget and admitted simultaneous buffers. A producer need not be a new thread: the controller could submit a wave, prepare a known immutable future plan, then join and commit in order. Immediate Future.result loops currently prevent that schedule.

Scheduling equations and assumptions

For batch i, let P be serial preparation and C the parallel consumer. With two buffers, preparation starts after input readiness, any result dependency, the preceding preparation, and release of the buffer used by batch i−2. One buffer additionally waits for the preceding consumer.

Pstart[i] = max(inputReady[i], dependencyReady[i], Pend[i−1], Cend[i−2])
Pend[i] = Pstart[i] + p
Cstart[i] = max(Pend[i], Cend[i−1])
Cend[i] = Cstart[i] + w
One buffer: also require Pstart[i] ≥ Cend[i−1]
Prior-result dependency: dependencyReady[i] = Cend[i−1]

The toy assumes independent stage execution, no GIL serialization, no memory-bandwidth contention, no extra packing/locking cost and admitted storage. Those are conditions to establish in a real prototype, not facts supplied by adding a second buffer. Buffering more batches cannot outrun a persistently slower producer or remove a genuine result dependency.

01 / The complete receiver

Where the work waits.

Each public slot passes through acquisition, fine inference and physical completion. Select a stage to inspect the available parallel work, its current ownership boundary and what must remain ordered. This is a dependency diagram—not a measured thread timeline.

↻Recurring keyed bank preparation and reacquisition are charged again at the appropriate public ordinal. Unsuccessful candidates and noise-only listening remain real receiver work.

Two serialization layers

Across slots: the stream controller waits for a complete public window, prepares its bank and finishes its bit receiver before changing the single-owner native source address. Within fine tracking: the fixed-affine lane is pushed before the adaptive lane for each input chunk.

What may move, and what may not

Independent hypotheses and frequency cells can be evaluated concurrently. Each hypothesis’s temporal recursion, global pruning decisions and ordered message completion must stay correct. A larger batch must also fit admitted memory and preserve native buffer lifetimes.

The architecture is the native IndependentApskV2 / headless receiver. Robust GUI operation remains unavailable pending reconnection. See current architecture and the physical-completion contract.

Inspect worker CPU time separately from elapsed time

These counters sum CPU time spent by workers. Concurrent execution means they overlap in elapsed time. They are useful for finding repeated computation, but they are not a second stacked wall-time chart.

Gram validation (about 0.0725 CPU-seconds) is nested in model updates (about 0.2444 CPU-seconds). The same immutable Gram input is validated independently by coherence models; evolving covariance work remains model-specific.

What does “about three busy cores” establish?

The unmarked row-7 profile averaged 0.423 seconds to process four seconds of continued input, with 3.16 busy-core equivalents. That is aggregate CPU time divided by elapsed time, not a map of which hardware threads ran when.

It does not prove that nine specific threads were idle throughout, that the GIL accounts for a particular percentage, or that reaching twelve busy threads would yield a fourfold speedup. The current profile contains controller CPU work, native waits, concurrent numerical work and barriers, but no direct GIL-hold or per-thread scheduler trace.

Why is row 4’s conservative interval enormous?

The broad noise-only fallback spans 8,596 frequency points, 2,149 four-point tiles, 78 workspaces and two rays: 1,340,976 FFT products. Ordinary abbreviated kernel forecasts were about 5–6 s/s, already above real time.

One recurring two-unit sample took 2.189 seconds elapsed and 3.358 CPU-seconds, versus 0.413–0.498 seconds elapsed and about 3.03 CPU-seconds for its peers. The cause is not established. With only three outer observations and the declared family-wise log interval, that stall produces an upper bound near 1.706 × 10²³ s/s. It is an unresolved statistical interval, not a credible precise maximum.

The original adverse observation remains. Removing its influence would not make the ordinary broad search real time. Optimizing nominal fine tracking alone cannot resolve this acquisition bottleneck.

Six versus twelve: selected case

Separate matched six-second observations. More busy cores need not mean better elapsed throughput.

Keep all available logical threads as the portable default. Power limiting, one laptop’s pilot result or minor timing differences do not authorize a reduced global budget. A stage may dispatch fewer useful tasks without capping the whole receiver. High utilization is useful when input backlog and ready work exist; it is not a reason to manufacture work or keep threads busy unnecessarily. Maintain one numerical-library thread per outer worker to avoid nested oversubscription.

The hardware can sustain more compute

Checked register-resident AVX2 FP64 FMA work. Each primary allocation ran for 180 seconds; bars show the final 120 seconds.

Twelve workers delivered 11.0% more compute than six; the reverse-order revisit retained a 9.0% gain. This synthetic workload reached 11.45 busy logical CPUs. It is a hardware scaling reference, not a receiver throughput conversion factor.

Power is a constraint, not the diagnosis

Separate telemetry established sustained package-power limiting on the balanced laptop profile. It did not show thermal-limiter flags in that steady run. More threads lower sustained clocks, and SMT siblings share core resources.

Those limits help explain scaling and timing variation. They do not explain every receiver barrier or establish that its present three-core average is an unavoidable hardware ceiling. Streaming-memory throughput also failed to scale like register-resident FMA.

An isolated model rewrite has a ceiling

Doubling both mapping/statistics and model work would imply about 1.593× fine and 1.415× nominal service. That is a scenario to evaluate, not an achieved result. Fixed-affine persistence’s optimistic 5.6% share overlaps existing categories and must not be added as another independent gain.

05 / What to change next

Reduce work.
Then expose it well.

The ranking favors concrete source-derived opportunities with a bounded discriminator before a large rewrite. It is an engineering priority order, not a measured speed ranking. Expand each proposal for its constraints and a test that could reject it. Predeclare strata, sample budget and stopping rules; use the maintained abbreviated method rather than a routine full-duration or exhaustive campaign.

Already tested: do not repeat these unchanged

Ready-lane overlap

Six candidate jobs saved a paired median 0.818 ms, below the predeclared 3 ms gate. Nine jobs lost 0.924 ms. The positive result amounts to about 1.5% of fine time before live scheduling overhead. The private prototype was removed.

Tensor direct-DFT substitution

TF32x3, rounded TF32 and scaled FP16 passed bounded numerical checks but failed to improve integrated receiver time. Isolated FP16 transform gains did not survive surrounding costs. These implementations were removed.

Bigger batches without a new structure

Earlier mapped batch enlargement and grouped NumPy projection variants reduced calls or increased CPU work without useful elapsed gains. A new batch proposal needs a changed work layout, ownership boundary or reusable computation—not just a larger number.

Extent of the remaining opportunity: small isolated changes have bounded upside; the tested overlap is too weak to justify a live scheduler change. Combined native execution, broader acquisition tiles and carefully bounded slot pipelines remain plausible structural opportunities with unknown realized benefit. No current evidence supports promising full 12-thread saturation or a specific total speedup.

Know what each number means.

Current measurement receipts

    Source identity and coverage

    Receiver terms in the diagrams
    CFO
    Carrier-frequency offset: each possible offset is a search hypothesis. Independent offsets can be scored before final peak selection.
    r and Gram
    Compact correlations with the observation and inner products between templates. They summarize a block for the channel-state update.
    Channel taps
    Components representing delayed signal paths. This profiled geometry uses two taps, so its covariance matrices are only 2 × 2.
    Coherence models
    Independent assumptions about how quickly the channel changes: the default times are 0.5 seconds, 2 seconds and infinity.
    Fixed-affine and adaptive lanes
    The fixed initial timing/clock lane supplies operational DATA evidence. The adaptive lane tracks changing timing diagnostically; its full work is still executed and charged.
    H0 and quiet completion
    H0 is the null signal hypothesis. An exact-zero modeled signal does not imply silent received samples. Quiet completion still requires scored physical absence in the required slots.
    GIL
    Python’s global interpreter lock. Python object manipulation can serialize, while many native numerical calls release it. This report contains no measured GIL-held fraction.
    Global peak selection
    Nonmaximum suppression compares neighboring candidates after full search coverage. Increasing concurrency must preserve its deterministic decisions.
    Measurement definitions and limits
    • s/s: prepared processing seconds per second of received baseband. A point at or above 1 has no real-time margin.
    • Busy-core equivalents: measured CPU time divided by elapsed time. These are averages, not a scheduler trace or a count of physical cores permanently occupied.
    • Nominal: a bounded uninterrupted continuation with a two-second prefix and 1/2/4-second continuation, charged across a public slot. Prefix and finish are charged once.
    • Conservative: a separate complete-work bound including capped state work, noise-only fallback and required uncertainty/model gates. A point below 1 does not override an unsupported component.
    • Matched gains: identical source/input/allocation comparisons that toggle a specific path. Ratios between unrelated historical calibrations are not treated as matched speedups.
    • GPU qualification: earlier CUDA evidence is source-bound. The new GPU upload/accounting path has host-side tests but still awaits execution on a usable RunPod instance.
    Primary research and maintained contracts
    • NumPy thread safety: many low-level operations release the GIL. Python orchestration and shared mutable arrays still require care; a Python caller is not proof of GIL serialization.
    • SciPy parallel execution: distinguish outer worker dispatch from numerical-library threads and avoid accidental nested oversubscription.
    • Python 3.13 ctypes shared-library calls: ordinary CDLL calls release the GIL during the native call. Native waits are not automatically Python GIL-held time.
    • CUDA Best Practices: host/device transfer: minimize transfer overhead and batch work where useful; include staging and synchronization in the complete cost.
    • NVIDIA matrix multiplication performance: tile shapes, arithmetic intensity and launch granularity affect realized throughput. Older GPU examples in this guide are not an RTX PRO 6000 receiver forecast.

    These references support design reasoning. They do not qualify a proposed receiver implementation or replace matched local measurements.

    Maintained receiver contracts

    • Receiver CPU allocation contract: preserve the full available logical budget and avoid nested oversubscription.
    • Complete-receiver capacity contract: complete work, physical completion and bounded statistical testing.
    • Precision policy: prefer qualified reduced bulk precision and tensor-compatible work; retain explicit guards and fallback reporting.
    • GPU-assisted forecasting procedure: combine applicable GPU work demand with source-matched local CPU phase costs, not a universal GPU/CPU multiplier.
